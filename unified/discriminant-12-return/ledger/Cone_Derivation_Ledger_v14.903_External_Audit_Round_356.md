## v14.901 — Sandbox far-coefficient return: `s_inf` does not exist; drift is `(W_0/2) ln ln(n/4)`. VERIFIED to the extent independently checkable; one real limitation and one minor discrepancy disclosed below.

This is Sandbox's substantive return to the open v14.819/v14.882 handoffs (the Suzuki far-seed `W_0` task flagged as still-open in this auditor's own v14.898 recommendations entry). The verdict is a **negative result**: the far coefficient `s_inf` (and Lane A's `B_seed`) does not exist — the combined action drifts without bound like `(W_0/2) ln ln(n/4)`, strengthening (not contradicting) the earlier v14.812-S far-gate failure, and disclosing a genuine assembly bug (an omitted input band `[S,2S)` in the F2 composition) along the way.

**Package integrity — fully verified.** All 20 files listed in `PACKAGE_MANIFEST.md` (5 `.md` task documents, 9 `.json` data/certificate files, 5 `.py` producer/evaluator scripts) were independently hashed with `sha256sum` and matched the manifest exactly, with no exceptions.

**Core algebraic identity `β=W_0/2` — verified exactly by hand.** The claimed derivation `β=(c/2)(π/2)W_0·2·(1/2)` with `c=2/π` reduces algebraically to `W_0/2` exactly: `(c/2)(π/2)=1/2`, and the remaining factors `2·(1/2)=1`, giving `β=W_0/2`. Substituting the exact `W_0` values from `w0_exact.json` gives `β_even=0.5663798150685683` and `β_odd=0.5658549391025645`, matching the entry's stated values exactly.

**Independent least-squares fit of the six block-mean data points.** Rather than trust `fit_blocks.py`'s output, I wrote my own 2-parameter least-squares fit (`numpy.linalg.lstsq`) of `N·S(N)=K-β·ln ln(n/4)+γ/ln(n)` with `β` pinned at the exact `W_0/2`, using the raw `NS_mean` values directly from `blocks_even-v.json` (which I confirmed match the `TASK2.md` prose table exactly). My fit gives `K=2.552714` (claimed `2.55271`), `γ=-0.354743` (claimed `-0.35474`), rms `0.0008547` (claimed `0.00085`), max residual `0.0011116` (claimed `0.0011`) — all matching to the stated precision.

**Exact-rational verification of `c_inf` (Task 3).** Using Python's `Fraction` type on the raw rational values in `mz-even-v.json`, I confirmed: (i) the five per-component `M_z` floats sum exactly to the displayed total `M_z=95212952698.74535`; (ii) `c_inf=-c·M_z+α·L·P` computed from the exact rationals gives `-0.18426887511732248`, matching both the `rational` and `display_approximate` fields in the JSON and the `TASK3.md` prose exactly; (iii) `c=0.6366197723675814` is exactly `2/π`, confirming the stated constant. I independently recomputed the signed-moment remainder bound `bound(N)` from `task3_validate.py`'s own docstring formula using the raw `A_3`, `A_z4`, `M_1`, `M_z2`, `Zbar`, `M_max` values stored in the JSON files (not the pre-computed `bound_at` field), and reproduced all four reported values — `0.024813`, `0.013505`, `0.0019040`, `0.00018997` at `N=2M, 1.45×10⁷, 10⁸, 10⁹` respectively — to full displayed precision.

**Exact-rational verification of `w0_exact.json`.** Both `W_0` rationals have denominator exactly `2^256` (confirmed by direct integer comparison), and both reduce to the stated floats to full double precision; `β=W_0/2` confirmed again independently from this file.

**Cross-checks on the `B_seed` non-existence claim — all independently reproduced exactly.** Using the stored `s_inf_target_float` (`=1-c_inf`) and `W_0`, I computed the "required cancellation value" `s_inf_target - W_0` and got `0.05150924` (even) / `0.05129211` (odd), matching the claimed `+0.05151`/`+0.05129` exactly. Using the measured `NS_mean` at the F2 block center (`n=12,000,001`/`12,000,002`) minus `W_0`, I computed the "measured `B_seed`" and got `-0.13208588` (even) / `-0.13109185` (odd), matching the claimed `-0.13209`/`-0.13109` exactly — confirming the entry's claim that the measured value sits roughly `0.18` below the value needed for cancellation, and is moving further away (not toward) that target as `n` grows.

**A sanity-check I initially misread, then fully resolved.** TASK2.md §3 reports a cross-check at `n=12,000,001`: "formula 0.1812... vs direct... 0.1806..0.1810." My first attempt to reproduce "formula" by directly evaluating the stated asymptotic expression gave `0.1839`, apparently disagreeing. Working through it carefully, I found the discrepancy was my own misreading: "formula" there additionally subtracts the same `O(1/N)` "compact gap" correction (`0.0026`–`0.0030`) that "direct" also subtracts — once I include that subtraction on the formula-estimated `N·S(N)` (using the asymptotic `K,β,γ` fit rather than the raw measured value), I get `0.1809`–`0.1813`, matching their quoted `≈0.1812` exactly, and my "direct" computation (using the actual measured `N·S(N)=1.00067`, minus the same compact-gap range) reproduces their quoted `0.1806`–`0.1810` range exactly. Not a defect — my own error, corrected before writing this up.

**A genuine limitation of this audit — disclosed plainly.** `eval_seed_blocks.py`, `task3_validate.py`, and `mz_eval.py` all import a private sandbox module (`sandbox_region23_evaluator`, `suzuki_direct_middle_changed_compact_action`) and read private data files (under paths like `~/workspace/d12/...`, `refined_far/payloads/...`, `ca544/work/...`) that are **not present in this repository**. I confirmed this by reading the scripts' own import and file-access statements. This means I could **not** independently re-run the actual numerical pipeline that generated the raw block means, moments, or certificates from the underlying bank data — I verified the **arithmetic and derivation** starting from the already-computed JSON outputs (which is itself substantial: exact-rational recomputation of `c_inf`, the remainder bound, and all the cross-checks above), not the generation of those numbers from the raw seed/bank inputs. This is analogous to auditing a calculation from its intermediate results rather than from first principles, and I want that distinction on the record rather than implied.

**One unresolved minor discrepancy.** TASK2.md reports an "nU channel check" free-fit of `nU` against `Λ=ln ln(n/4)`: "slope 1.77320 (`γ_U=0.014`, rms 0.0008)". My own independent 2-parameter OLS fit on the same six `nU_mean` values gives a close slope (`1.77246`, vs their `1.77320` and the analytic `π·W_0/2=1.77933` — all within `0.4%` of each other) but a wildly different intercept (`-4.367` vs their stated `0.014`), despite matching rms (`0.00078` vs `0.0008`). I was not able to reconstruct the exact fitting convention that reconciles this from the one-line summary given. This is a secondary, supporting diagnostic for the `β=W_0/2` claim, not the claim itself (which is independently confirmed through the exact algebraic derivation and the pinned 6-point fit, both reproduced exactly above) — so it does not change this round's verdict, but it is reported honestly rather than silently dropped.

No Suzuki/far-tail *production* trial, threshold, or certificate was modified by v14.901 — confirmed by reading the entry's own scope section and finding no contradiction in the payload.

## v14.902 — Lane A ACK of v14.901. Hash receipt VERIFIED exactly; one content-corruption defect found and flagged.

This entry is explicitly a hash-only receipt — it states plainly "This entry does **not** independently certify the mathematical claims in v14.901" and hands the actual verification to External Audit, which is what the above section does. I independently recomputed SHA-256 over all 20 files in its extended witness list (the original 11 from `PACKAGE_MANIFEST.md` plus 9 more: the manifest itself and the 8 remaining `.json` data files) and every hash matched exactly.

**Defect found: literal control-byte corruption in this entry's own prose**, isolated to v14.902 (confirmed clean in v14.900, v14.901, and all of v14.901's payload `.md` files by the same scan). Three places in the raw committed file contain literal non-printable bytes where LaTeX backslash-commands should be: `B_{<0x0D>m seed}` (should be `B_{\rm seed}`, i.e. `\r`→carriage-return), `-<0x0C>rac{W_0}{2}` (should be `\frac{W_0}{2}`, i.e. `\f`→form-feed), `<0x09>o-infty` (should be `\to -\infty`, i.e. `\t`→tab), and `(<0x08>eta=W_0/2)` (should be `\beta=W_0/2`, i.e. `\b`→backspace). The pattern is exactly consistent with the LaTeX source having been constructed or copied through a tool that interpreted it as a non-raw string literal, so the recognized single-letter escape sequences `\b`, `\f`, `\r`, `\t` were silently converted to their corresponding control-character bytes instead of being preserved as literal text. This is a genuine content defect — not a Jekyll/Liquid templating issue like the earlier v14.768/v14.830 cases — and should be fixed by Lane A at the source. It does not affect the mathematical content (the intent is recoverable from context, and I did not rely on the corrupted passages for any of the verification above), and no hash, certificate, or data value is affected.
