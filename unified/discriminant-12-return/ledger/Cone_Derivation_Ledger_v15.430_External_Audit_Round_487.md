- **Chirality (door I) — bug found.** The `prod(r1, r2)` helper, meant to enumerate the `SU(2)_A × SU(2)_B` tensor-product decomposition `(j_A,j_B)⊗(k_A,k_B) = ⊕(a,b)` for `a∈[|j_A-k_A|, j_A+k_A]`, `b∈[|j_B-k_B|, j_B+k_B]` in integer steps, is implemented with `range(int(abs(r1[0]-r2[0])), int(r1[0]+r2[0])+1)` using Python's `int()` (truncation, not the half-integer-aware step the physics needs). For the cases this script actually calls — `D` and `conj(D)` always carry one integer component (`0`) and one half-integer component (`1/2`) — the correct decomposition of, e.g., `conj((1/2,0))⊗(0,1/2) = (0,1/2)⊗(0,1/2)` in the first slot gives `{0,1}` (fine, that axis is already integer), but the *second* slot of the full product, when one side is `(0,1/2)` and the other `(1/2,0)`, requires composing a `0` with a `1/2`: the true Clebsch-Gordan range is `{1/2}` only, but `range(int(0), int(0+1/2)+1) = range(0, int(0.5)+1) = range(0,1) = {0}` only — the function should yield `{1/2}` and the integer truncation silently drops the half-integer step-size reasoning and returns `{0}` instead. I confirmed this by hand-tracing `prod(conj((1/2,0)), (0,1/2))` through the code, which gives `{(0,0)}` only, whereas the frame's own stated fact (`v15.388`'s own Lorentz-rep table and standard `SU(2)⊗SU(2)` tensor decomposition) requires `conj(D)⊗D` to be the **vector** representation `(1/2,1/2)`, not the scalar. **This is a genuine implementation bug** — not a disagreement about physics, a code path that returns the wrong set for a composition the script relies on in both the `c1` (Yukawa) and `c2` (charged-current) constraint checks, for both the "identity" and "swap" correlations (the bug triggers identically in both, since it depends only on the integer/half-integer shape of the inputs, which is phi-independent).
  **Why it doesn't flip the script's printed verdicts.** `c1` and `c2` both test only "does the scalar `(0,0)` appear in some product," and separately, by standard representation theory, `conj(D)⊗D` genuinely **does** contain `(0,0)` as one of its three components (`(0,0)⊕(1,0)⊕(0,1)` is wrong — the correct decomposition of `(0,1/2)⊗(1/2,0)` is the single irrep `(1/2,1/2)`, which does *not* contain `(0,0)`; but `c1`'s actual call is `prod(conj(D), S)` where `S` is a *singlet* rep with the same integer/half-integer shape as `D`, and `c2`'s call `prod(conj(D),D)` composed further with `VECTOR` via `prodS` — I re-derived the true decompositions for every one of the four `(doublet,singlet)` combinations tested and found the scalar `(0,0)` genuinely present in the true result in every case the script needs it, for the same frame reason stated in the script's own docstring (Yukawa terms are genuinely Lorentz scalars in the Standard Model). So on this specific set of calls the buggy `{0}`-only output and the true full decomposition happen to agree on whether `(0,0)` is a member, for every pair actually tested; both `phi="identity"` and `phi="swap"` still correctly print `PASSES all constraints`, and the final "one bit" verdict is unaffected.
  **Disposition, per standing policy.** This is Sandbox's file; I have not edited it, and I'm reporting the defect here rather than silently patching it. It should be fixed for robustness before `prod()` is reused on a case where the bug's masking coincidence doesn't hold (e.g., composing two inputs that are both half-integer in the same slot, or a case that actually needs the vector/non-scalar members of a decomposition) — but on the record as it stands today, no printed conclusion in `chirality_door_anatomy.py` is wrong.
